## 2. R-12：TCP Unit ID 扫描

### 2.1 设计

- **探测规则复用**：`UnitIdScanOptions.ToProbeOptions()` 把 Unit ID 范围映射为 `DeviceScanOptions`，
  因此 TCP 与串口两条路径的判定规则**完全一致**（默认 03→04→01→02；手动模式仅允许 01/02/03/04；
  合法异常响应判在线；校验错误只记“疑似”；绝不使用写功能码与广播地址 0）。
- **默认串行**（并发度 1，复用当前会话，满足 CC-1）；并发 ≥2 时通过 `TcpSessionFactory` 为额外 worker
  建立**临时 TCP 连接**，扫描结束一律释放。工厂契约是“返回已打开的会话”，
  返回未打开的会话时服务会**明确降级为串行并给出原因**（不把 Unit ID 静默记成“未发现”）。
- **每个 Unit ID 恰好探测一次**：用 `Interlocked.Increment` 分配单元，并发下无重复、无遗漏。
- 单个 Unit ID 探测异常（含链路中断）不会中断整轮扫描，记为未确认并继续。
- 结果字段与设备扫描一致（在线状态/探测功能码/异常码/首末时间/耗时/确认次数/设备标识/备注），
  另加 `WorkerIndex` 便于诊断并发分配；支持 CSV 导出、设为默认 Unit ID、保存为设备目标、扫描方案（`unitid`）。

### 2.2 并发与安全

- 并发上限 8；界面在并发 >1 时**二次确认**（网关常限制并发连接数，且扫描会占用总线）。
- 参数门禁：Unit ID 1~247（**0 被拒绝**）、超时 50~10000 ms、间隔 0~5000 ms、确认 0~5 次、
  并发 1~8；写功能码一律 `VAL-4006` 拒绝，即使绕过界面直接调服务也会抛 `CommException`。

### 2.3 测试（19 个用例，`tests/Comm.Scanning.Tests/UnitIdScanTests.cs`）

串行扫描只读且不广播、异常响应判在线、并发有界（模拟器观测最大在途 ≤ 并发度）且每个 Unit ID 只探一次、
临时会话被释放、工厂失败/返回未打开会话时降级、取消、暂停门、参数校验（7 组理论用例）、
手动模板、耗时估计（含并发折算）、CSV 导出、进度上报完整性。

## 3. 性能与稳定性

### 3.1 探针（`tools/Comm.StressProbe`）

本机实测（60 s @1000 帧/s + 20 万条显示缓冲，报告见 `docs/stability-probe-report.md`）：

| 指标 | 实测 | 目标 | 结论 |
|---|---|---|---|
| 落盘记录完整性 | 59 990 / 59 990 条 | 不丢 | 通过 |
| 总线+落盘处理能力 | ~1.9 M 帧/s | ≥ 1000 帧/s | 通过（约 1900 倍余量） |
| 显示缓冲 20 万条保留 | 200 000 条 | 全部保留 | 通过 |
| 进程内存（含 20 万条缓冲） | ~148 MB | < 500 MB | 通过 |
| 过滤首屏（按会话，20 万条） | ~2 ms | < 1000 ms | 通过 |
| RTU 成帧吞吐 | ~1.7 M 帧/s | ≫ 1000 | 通过 |
| 回环事务往返（软件上限） | ~47 000 次/s | 参考值 | — |
| 导出 CSV（20 万条） | ~250 ms | 参考值 | — |

> 这些是**软件上限参考值**（回环传输、无界面渲染、无真实硬件）。
> “1000 帧/s 下界面仍可操作”“真实适配器吞吐”“24 h 不泄漏”仍需目标机实测（第 6 节）。

### 3.2 稳定性长跑（`tools/Invoke-SoakTest.ps1`）

- `-Quick`：总时长 5 分钟、每轮 10 s（提交前冒烟）。本机结果：18–20 轮、失败 0、内存 258.2 → 262.3 MB（漂移 4.1 MB）。
- 默认：24 h、每轮 60 s。每轮读探针输出的 **JSON 摘要**（不解析中文控制台输出，避免 PowerShell 5.1 的 OEM 代码页乱码）。
- 报告 `docs/stability-report.md`：每轮时间/用时/内存/退出码/结论 + 内存漂移 + 判定标准。

### 3.3 本机内存基线说明

探针每轮都会新建 20 万条显示缓冲（约 100–150 MB），因此**单轮内存 ~260 MB 属正常**；
稳定性判据看的是**跨轮漂移**（每轮结束后进程退出、内存应回到同一水平），而不是单轮绝对值。

## 4. 本轮发现并修复的真实缺陷

> 三个缺陷都是**新写的探针/回归用例发现的**，不是表面优化；每个都补了测试或断言防止回归。

### 4.1 队列轮询导致每次事务多等 5–15 ms（性能）

`ModbusMaster.DispatchLoopAsync` 在无请求时用 `Task.Delay(5)` 轮询三个优先级队列，
每个事务因此至少多等一个节拍。性能探针实测**回环往返仅 63.7 次/s**。

修复：引入 `SemaphoreSlim` 作为“队列到达”信号（入队后释放，调度循环等待信号，100 ms 兜底仅防御信号丢失）。
修复后回环往返 **49 872 次/s（约 780 倍）**。

### 4.2 写请求可以被“扫描/周期”优先级队列发出（安全，SR-2）

事务层守卫只检查“是否已确认、是否广播”，**没有检查优先级**。这意味着监视表刷新（P1）或扫描任务（P2）
构造一个 `Confirmed=true` 的写请求就能绕过“写操作只允许交互式请求”的约束（规划 13.3 / CC-6）。

修复：`GuardReject` 增加优先级校验——写请求必须为 `RequestPriority.Interactive`，否则 `VAL-4006` 拒绝。
新增 `Comm.Security.Tests` 用例 `SR2_Write_request_from_periodic_or_scan_priority_is_rejected`。

### 4.3 落盘与日志的 `WrittenCount` 统计的是“批次”而不是“条数”（正确性）

`FrameFileWriter._written` 与 `RollingFileWriter._written` 在**每批刷新**时 +1，但属性名与用途是“已写入记录/行数”。
性能探针因此报“落盘 317 条 / 5000 帧”的假缺陷（实际文件 5001 行，数据没丢）。

修复：按批次实际条数累加（`Interlocked.Add`），语义与命名一致；探针的“落盘完整性”now 是硬断言。

### 4.4 其他小修

- `LoopbackChannel(responseDelayMs: 0)` 会调用 `Random.Next(1, 1)` 抛 `ArgumentOutOfRangeException`（性能探针暴露）。
- `UnitIdScanService` 对工厂返回“未打开会话”的情况不再静默产出“未发现”，改为降级 + 可读原因。
- `UnitIdScanView` 只读属性 `DetailText` 绑定到 `TextBox.Text`（默认 TwoWay）导致界面线程异常 → 显式 `Mode=OneWay`
  （冒烟测试发现，属 M4 期间新增页面的缺陷）。
